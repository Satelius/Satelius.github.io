00 / 核心结论

Harness 不是第四个仿真器，也不是第二套场景格式。Harness 是一层执行治理契约：它明确谁能被调用、调用的是哪个版本、使用了哪些依赖、产生了哪些证据，以及这次结果是否具备发布资格。
一句话辨认边界

scene_gen 回答“场景是什么、物理是否通过”。

Harness 回答“谁在何种条件下产生了这个结果”。

01 / 先认识现有项目

在 Harness 出现以前，
项目已经走通了什么？

如果读者第一次接触这个项目，最先需要建立的认识是：系统不是直接把文本交给仿真器。系统先逐层缩小不确定性，直到一句语言请求变成可以复查、可以重放、可以验证的物理场景。

STAGE 0 · BOUNDED INPUT 00

系统先决定哪些话可以被理解。

受限解析器只接受桌面物体、颜色、材质、区域和少量空间关系。路径、资产编号、坐标、四元数和可执行代码都会在进入场景语义之前被拒绝，因此用户只能表达“想要什么”，不能偷渡“后端怎样实现”。

02 / 契约提出的改变

六个内部阶段，
收拢成三个公开 Skill。

外部调用方不需要理解解析器、求解器和 builder 的每个内部函数。调用方只需要面对三个职责稳定的接口：先编译场景，再回放物理过程，最后判断是否具备发布资格。

现有内部路径
012345

text2env.compile@1.0.0

把语义请求变成不可变的场景包引用。

compile 复用项目现有的受限解析、资产 grounding、受限求解、builder 和静态 validator。Harness 只为这组既有行为补上稳定的输入、输出、版本和审计边界。

最容易误解的一点

compile 的 RunState 可以是 succeeded，同时静态验证报告仍是 incomplete。前者表示编译接口正常产出了类型化结果；后者表示真实物理证据还没有产生。

03 / 先拆开四个词

“成功”不是一个
可以包办一切的状态。

读者需要同时观察执行、验证和发布三个层面。只看一个绿色的 “PASS” 会隐藏真正的问题，因此契约刻意把这些概念分开记录。

场景 A · 编译刚结束

编译接口已经完整返回，但运行时回放尚未开始，所以系统还没有物理证据。

RunState.statussucceeded 接口是否正常产生结果
validation_statusincomplete 物理与门控检查的结论
publishablefalse 是否满足全部发布前置条件
published未定义 契约不执行外部发布副作用
因此，“编译成功”只能证明场景包被正确生成，不能证明场景已经通过物理验证。
RunState 只记录执行生命周期

blocked 表示输入、依赖、资产、求解或门控按规则拒绝了这次请求。failed 表示 Registry、适配器或 handler 出现了契约之外的意外缺陷。

05 / 相邻的资产契约

在调用 Skill 以前，
系统还要先认识资产。

Harness 负责记录一次工作怎样被执行，但它不会凭空知道“这个杯子是什么颜色、应该怎样立在桌上”。这些资产事实来自另一份契约：asset_ledger.v3。下面用三页把它讲清楚。

PAGE 01 · WHAT IS AN ASSET LEDGER?

先把它理解成一份
“资产档案”。

机器人看见的“杯子”，在仿真器里其实是一组文件和测量结果。系统需要知道它叫什么、哪个模型是红色、怎样放才稳、有没有内腔、SAPIEN 应加载哪个文件，以及这个文件是否真的通过过检查。

ledger.json 把这些事实放在同一份记录里。每个资产一份 ledger；同一资产可以包含多个 model，每个 model 又可以有 SAPIEN、Isaac 等不同后端表示。

最重要的理解ledger 记录“资产本身的事实”，不是记录一次场景运行。

PAGE 02 · TWO CONTRACTS, TWO QUESTIONS

Ledger 管资产。
Harness 管执行。

两份契约都在追求“可信”，但它们验证的对象不同。ledger 证明一个具体资产有哪些可信事实；Harness 证明一个具体 Skill 版本在什么输入和依赖下完成了什么工作。

Text2Env 不直接翻阅所有 ledger。资产管线先把已经筛选过的事实投影成 asset_catalog.json，compile 再把这份 catalog 当作不可变依赖使用。

不会冲突的原因两边的“唯一权威”各有范围：一个管资产事实，一个管调用事实。

06 / 身份与版本

每一次调用，
都必须说清“具体是谁”。

“调用最新版本”看似方便，却会让昨天可复现的结果在今天悄悄改变。契约因此禁止版本范围、隐式 latest 和静默回退，每次调用都必须给出精确的 SemVer。

规范身份 ( skill_id, version ) text2env.compile@1.0.0
机械派生 MCP 名称
协议工具名称 dot → underscore text2env_compile_v1_0_0
MAJOR

旧消费者必须重新理解

删除或重命名字段、增加必填字段或输出字段、收紧输入、改变默认值、状态含义、确定性或发布门控，都必须提升主版本。

MINOR

旧消费者可以故障关闭

增加不改变默认行为的可选输入、扩大输入范围、加入现有制品集合，或新增故障关闭 blocker 代码，需要提升次版本。

PATCH

公共形状与语义保持不变

实现缺陷得到修复，但公共 schema、状态含义和声明语义都没有变化时，只提升修订版本。

INVOCATION DIGEST LAB

什么改变调用身份，什么只改变存放位置？

Registry 会把默认值展开，把依赖按名称排序，并把制品 URI 替换为内容身份。这样，文件换了目录不会伪装成新内容，而请求文本、seed、依赖摘要或 Skill 版本的变化一定会留下新的调用摘要。

canonical invocation
{
  "skill_id": "text2env.compile",
  "skill_version": "1.0.0",
  "request": "Place a can on top of a plate.",
  "seed": 42,
  "artifact_identity": "application/json|null|8ba15e...",
  "dependency_sha256": "8ba15e84...",
  "max_attempts": 1
}
SHA-256 计算中... 基准调用身份

run_id、时间戳、事件、输出目录和 URI 不进入 invocation_digest。

EnvironmentPackage 是什么？

它是现有场景包的不可变引用，不是第二套包格式。

这个引用把 `package_id`、生产 Skill、seed、SceneSpec 摘要、ResolvedScene 摘要、资产目录引用和包清单引用放在同一条严格记录中。Harness 由此能够验证“这次回放使用的包”确实是“那次编译产生的包”。

11 / MVP 边界

一份可信的契约，
也要明确自己不做什么。

这份 MVP 只治理当前已经存在且可以验证的 Text2Env 路径。把未实现能力提前写入统一接口，会让调用方误以为系统拥有并不存在的保证。

IN SCOPE · 本契约负责
  • 受限自然语言到场景包的编译
  • RoboTwin / SAPIEN 物理回放
  • 包、哈希、物理和视频验证
  • Skill 注册、精确版本与审计记录
  • 发布资格判断，但不执行发布
OUT OF SCOPE · 本契约不承诺
Anchor2Env网络资产搜索第二仿真器Transfer插件热加载分布式调度策略执行数据采集训练评估

这些能力以后可以形成新的 Skill 或新的契约，但不能绕过当前 `scene_gen` 的哈希绑定与物理验收边界。
