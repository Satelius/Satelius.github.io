04 / TAKEAWAYS

目前最值得讨论的
三个启发。

01

看见目标，不等于会选动作。

已观察：P8 校准后仍在左右往返，67 步没有抓取。部分文字描述与所选方向矛盾。

推断：下一步重点应是图像关系到物理动作的对应，不能把所有失败继续归因于相机。

02

预算加倍，可能只是多绕几圈。

已观察：三次扩预算均未成功；总步数、阶段预算、重规划次数、仿真时限各自可能先耗尽。

边界：样本少、模型有随机性；只能说明这些尝试没获益，不能证明预算永远无用。

03

“快脑”要测出来；教师要先会做。

已观察：云端 Luna 仍有秒级延迟；官方 2B 模型尚未本地验证。

待验证：本地小模型可能更适合局部执行。当前失败轨迹需筛选或纠正，不能直接拿来教正确动作。

我们怎样避免把测量误当结论？

任务成功只认 RoboLab 原生判定。“抓取后抬升 3 cm”只是代理事件，尚不能证明持续持物；缺失数据保留未知。日志与静态调用链支持真值隔离，但尚无完整的出站请求独立审计。单次每格的比较只反映工程趋势。

05 / NEXT STEPS

先让闭环可靠，
再谈小模型与蒸馏。

  1. 补齐带视频的固定基线

    在 provider 门禁通过后，新建 11 × 3、80 步矩阵。成功率、阶段进展、时延分开汇总；旧 P9 v2 保留为未完成历史记录。

  2. 每次只补一个作者功能

    先方向约定，再输出协议、本体反馈、阶段管理、动作历史、失败恢复、自适应步长与选择性动作分块；逐版本同配置、同任务、同 seed 对比。

  3. 测官方 2B，确定它适合什么角色

    按仿真适配器 → 真实机器人适配器 → 未微调基座 → Astra + 2B 的顺序。先查显存与服务共存，再测实际闭环速度。

  4. 有可靠示范后，再做最小训练对照

    比较动作监督、阶段条件监督与纠正轨迹；按完整 episode 划分训练/测试。在线学习与动态路由暂不实施。
